# gfx1100 — Radeon 7900XTX, RDNA3 / Navi31

Living lever map for gfx1100. See [README.md](README.md) for the method + instrument→lever table.

## Silicon
96 CU, 6 Shader Engines, 2× SIMD32/CU, wave32, max 32 waves/CU, 64KB LDS/workgroup, 2526 MHz.
24GB GDDR6, **~960 GB/s**. **6MB L2 + 96MB Infinity Cache (MALL). 128-byte cacheline.** VOPD dual-issue.
Has WMMA (fp16/bf16/int8 matrix cores). **No native FP8/FP4** — int8/fp16 is the precision floor.

## RESOLVED (2026-07-05): MALL-resident, NOT DRAM-thrash — cache-residency thesis FALSIFIED
**Reread-BW microbench (`autoresearch/harness/mall_probe.hip`) settled it:** effective reread bandwidth on
gfx1100 is 1.6–4.6 TB/s across 16–96MB and **never drops to DRAM peak (960 GB/s)** even at 224MB (2.3× the
MALL). The 96MB Infinity Cache catches the L2-misses at multi-TB/s. **gfx1100 is MALL-resident; the 16% L2-hit
is a red herring.** The NT/SLC cache-residency campaign was FALSIFIED empirically: qkvza (16% L2-hit, the
"worst thrasher") REGRESSED -2.11% with SLC (prechecks passed) — you don't stream past a cache serving 4 TB/s.
Every SLC variant across moe_down/gate_up/qkvza/residual: DEAD. **Do NOT re-run cache-residency levers on gfx1100.**

**So the gfx1100↔gfx1201 ratio (1.10 despite 1.5× BW) is NOT a cache problem.** The real bottleneck is the
**batch-1 latency chain** (dequant→FMA→reduce dependency, bounded by MALL+compute latency, ~arch-invariant),
i.e. the earlier "decode is GPU-bound but batch-1 latency-limited" finding, now proven from the memory side.
Next campaign target is critical-path latency (VOPD dual-issue, shorter dequant chain) or batching (spec-decode/MTP),
NOT cache. FETCH_SIZE/GL2C_EA_RDREQ_*B wiring into the profiler is still worth doing to surface MALL-hit directly.

## (superseded) earlier framing: LOW L2-hit — but MALL is DARK
Census on the decode kernels shows **L2-hit 12-20%** (qkvza 16%, gate_up 20%, residual 13%) vs
**gfx1201 = ~77% on the SAME kernels.** So gfx1100 misses L2 4× more often, and `mem_busy` is only 44-60%
(latency-bound, not bandwidth-bound) — the 1.5× bandwidth is unused.

**CRITICAL CAVEAT (2026-07-05): "L2-hit 16%" does NOT by itself prove DRAM-thrash.** The L2-miss traffic goes
to the 96MB MALL (Infinity Cache) *before* DRAM. If the MALL catches it (~100ns) gfx1100 is fine; if it falls
through to DRAM (~300ns) it thrashes — and L2-hit alone can't distinguish them. Our old `dram_miss` field is
literally `GL2C_MISS` = an L2-miss MISLABELED as DRAM (fix pending: rename → `l2_miss`).
**Corollary — Q1 no-op is consistent with MALL-resident:** moe_down L2-hit 35.7%, SLC bypass did nothing; if
the misses were already MALL-caught, keeping x/KV in L2 changes nothing. **DO NOT treat DRAM-thrash as established.**

**BUT rocprof CAN measure it on RDNA3 (corrects an earlier "can't"):** these ARE gfx11-available —
`FETCH_SIZE` (KB fetched from video memory = real DRAM read bytes, *after* MALL) and the sized
`GL2C_EA_RDREQ_{32,64,96,128}B` (L2→fabric read bytes). So:
```
MALL-hit% ≈ 1 − FETCH_SIZE_bytes / (Σ GL2C_EA_RDREQ_sizeB × size)     # L2-miss bytes that never reached DRAM
```
(The aggregate `GL2C_EA_RDREQ` is gfx12-only and `TCC_EA_RDREQ_DRAM` is CDNA-only — but the SIZED EA variants
+ `FETCH_SIZE` cover gfx11.) **Validate `FETCH_SIZE` semantics first** (video-memory interface vs L2-boundary)
with a MALL-residency microbench: reread a 32MB buffer (fits 96MB MALL, blows 6MB L2) N times — FETCH_SIZE ≈
32MB ⇒ FETCH_SIZE is true DRAM + MALL engaged + formula valid; ≈32MB×N ⇒ metered at L2 (or MALL not engaged) ⇒
the 16% really is DRAM-thrash. That microbench is the elevated Q6 and the decisive test — run it BEFORE
over-investing in the SLC forks. Ground-truth remains tok/s (Q1's no-op already says residency wasn't the
bottleneck there).

### The cache-residency lever (top priority, arch-specific → FORK)
- **SLC/streaming (non-temporal) loads on the write-once expert-weight stream** so it bypasses cache and stops
  evicting the reused activation x + KV. Look up the RDNA3 cache-control bits (GLC/SLC/DLC) on `global_load_*`.
- Keep x / KV / scales resident (cache-hint or LDS-stage them).
- **Verify the MALL is even engaged** — 16% hit with 96MB is suspicious on its own (check amdgpu MALL enable +
  the access pattern that triggers MALL residency). This lever is gfx1100-SPECIFIC (gfx1201 is already
  L2-resident and would be HURT by streaming) → must fork to `fused_qkvza_hfq4g256.gfx1100.hip` etc.

## Other compute levers (when the census says compute/occ, not cache)
- **VOPD dual-issue** — 2 independent FP32 ops/cycle; structure reductions/FMAs as independent dual-issuable pairs.
- **`global_load_lds`** — direct global→LDS, async: prefetches AND frees VGPR (use at the occupancy cliff).
- **fdot2 / dp4a (sdot4)** — fp16 / int8 dot products.
- **`v_perm_b32` / `v_cvt_f32_ubyte0..3`** — fast nibble/byte dequant, shorten the mq4 dequant chain.
- WMMA fp16/bf16 is present but scalar MMQ is chosen for the HFQ4 GEMM (iu8-WMMA lost + coherence-falsified,
  2026-06-26); a low-register fp16-WMMA reduction is UNEXPLORED.

## Wins / deads on record
- **v1 traffic-cut** (row-reuse on virgin GEMVs): WON, +14.75% → baseline_v1.
- **v3 attention register-ring P=4** (0.5%-occ kernel, per-wave MLP): WON +6.95% → baseline_v3 (175.6 tok/s). UNIVERSAL (shared).
- **occupancy levers** (raise occ): DEAD — batch-1 GEMV is work-limited, occ is structural.
- **per-wave MLP on qkvza/gate_up** (v4 prefetch/oct-unroll): DEAD/regress — occ 32-50% already has TLP hiding
  latency; MLP redundant. The lever there is CACHE-RESIDENCY (above), not MLP.
- Lesson: per-wave MLP wins ONLY on latency-exposed LOW-occupancy kernels (attention 0.5%). Everything else at
  moderate occ + low L2-hit → cache-residency.
