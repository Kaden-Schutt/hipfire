# Qwen 3.8 27B — day-zero readiness

**Date:** 2026-08-14 · **Status:** analysis complete, no code changes made or needed
**Method:** upstream `config.json` / `tokenizer_config.json` metadata only (no weights
downloaded), diffed against the configs hipfire already loads.

## Verdict

**Nothing structural to change.** Qwen 3.8 self-identifies as the Qwen3.5 family and
every field it carries already appears in `Qwen/Qwen3.6-*`, which hipfire ships support
for. The `Qwen3.8-2.4T-A95B` config was used as the architecture proxy because the 27B
was not yet published when this was written.

### The "39 new fields" were a nesting artifact

3.6 is VL-wrapped (`Qwen3_5ForConditionalGeneration` + `vision_config`), so its fields
live under `text_config.*`. `Qwen3.8-2.4T-A95B` is text-only, so the same fields sit at
top level. Both the router and the parser resolve this with one identical line, so the
un-nesting is a no-op. Fields that looked new and are not:
`attn_output_gate`, `head_dim`, `partial_rotary_factor`, `rope_parameters.{rope_theta,
rope_type,partial_rotary_factor}`, `layer_types`, `linear_conv_kernel_dim`,
`linear_{key,value}_head_dim`, `linear_num_{key,value}_heads`, `mamba_ssm_dtype`,
`mtp_num_hidden_layers`, `mtp_use_dedicated_embeddings`, `output_gate_type`,
`full_attention_interval`, `router_aux_loss_coef`, `shared_expert_intermediate_size`.

Present in 3.6 and absent from the text-only 3.8 proxy (all safely defaulted):
`vision_config.*`, `image_token_id`, `video_token_id`, `vision_{start,end}_token_id`,
`language_model_only`, `rope_parameters.mrope_interleaved`,
`rope_parameters.mrope_section`.

## Day-zero checklist

1. **Config diff — the whole gate.** Pull `config.json` alone (a few KB; do **not**
   pull weights yet) and diff its key set against `Qwen/Qwen3.6-27B`'s `text_config`.
   Empty diff → load it. If it ships VL-wrapped like 3.6-27B did, it is shape-identical
   to what we serve today.
2. **Confirm arch id before quantizing.** `hipfire-quantize` stamps from top-level
   `model_type`. Expect `qwen3_5_text` → 5 (dense) or `qwen3_5_moe_text` → 6. A
   `model_type` literally containing `3_8`/`3.8` is the one string that would fall
   through to arch 0 (llama) with only a warning — if that happens, pass `--arch-id 5`
   (or 6) explicitly and add the string to `auto_arch_id`, `derive_arch_id`, and the
   `hfq.rs` provenance list. That is the only anticipated code change, and it is three
   string literals.
3. **Quantize + load smoke**, then the serve route per
   [`docs/VALIDATION.md`](../VALIDATION.md) — `scripts/serve_harness.py battery`
   against the exact artifact. Read the decoded text; numbers alone never prove
   coherence.
4. **Only then** benchmark, following
   [`docs/methodology/perf-benchmarking.md`](../methodology/perf-benchmarking.md).

## Residual risks, ranked

1. **New `layer_types` value.** Anything other than `linear_attention` collapses to
   `FullAttention` (`qwen35.rs:518-528`) with no error. A 3.8 that introduces e.g. a
   distinct sliding-window kind would load the wrong kernel family and fail as a
   missing-tensor panic or as silently wrong output. **Check the `layer_types` value set
   first** — it is a one-line jq and it is the highest-consequence unknown.
2. **`num_experts` / `num_experts_per_tok` scale.** The Max proxy is 512 experts,
   top-10. A 27B MoE at that fan-out would meet the EP/TP refusals (`tp_size != 4`,
   `layer_types` length checks, `head_dim % 32`). Dense 27B is unaffected.
3. **`linear_num_value_heads`** jumps 48 (3.6-27B) → 128 (Max). Read from config, so it
   only affects DeltaNet buffer sizing at Max scale.
4. **MTP.** `mtp_num_hidden_layers: 1` matches 3.6; the MTP head is a separate artifact
   and needs no config work, but MTP requires `mode = "mtp"` to be selected or the head
   loads and the speculative loop never runs (see `serve_harness.py`'s note on this
   exact failure — gen=0 with no error envelope).

## Non-risks, recorded so they are not re-litigated

- Tokenizer/vocab: unchanged from 3.6. Our Qwen3.5 tokenizer covers it.
- DeltaNet/linear attention: already shipped and data-driven.
- `eos_token_id: 248044` in config vs `<|im_end|>` (248046) as the tokenizer's
  `eos_token`: 3.6 has the identical discrepancy and serves correctly, so this is not a
  3.8 regression.
