  Confirmed via `scripts/coherence-gate.sh` — all 6 prompts incoherent.
- ❌ Same gibberish even with `HIPFIRE_MMQ_K_FILTER=4096` (only attention

  uses MMQ). One MMQ call per layer is enough to break output.

## What we've localized

Diagnostic flags wired into `gemm_hfq4g256_residual_mmq_gfx906`:

| Flag | Behavior | Output |
|---|---|---|
| (default) | run MMQ kernel for the residual GEMM | gibberish |
| `HIPFIRE_MMQ_DIAG_PASSTHROUGH=1` | skip MMQ, forward to FP16 wave64 | coherent |
| `HIPFIRE_MMQ_DIAG_QUANTIZE_ONLY=1` | run quantize, then forward to FP16 | coherent |

So:
- Dispatch wiring is correct (passthrough produces coherent output).
- Q8_1 quantize kernel is correct (quantize-only produces coherent output).
- The dp4a kernel **body** is what's producing wrong output in production.

## Why standalone passes but production fails

The standalone correctness test uses synthetic uniform-random weights and
activations. Real Qwen weights have:

- Weight scale magnitudes that span ~6 orders of magnitude across rows
  (per-group scale varies layer-to-layer and within a layer).
- Per-group `(scale, zp)` pairs occasionally near FP16 representable
  limits.
- Activations after layer-N have distributions very different from
  layer-0 (residual stream grows roughly linearly with depth).

Suspected: an edge case the synthetic test doesn't hit. Candidates:

1. **Weight-distribution edge case.** Specific (scale, zp) combinations
   (e.g. very small scale × very large zp) trigger numerical breakdown.
   Real Qwen weights may include such groups; synthetic uniform doesn't.
2. **Activation magnitude during prefill.** Q8_1 dynamic-scales each
   32-K-element block; if the per-block scale is very small and the
   per-block sum is very large, `zp_w * sum_x` dominates and any error
   in `sumi` becomes catastrophic.
3. **Cross-layer state.** Q8_1 scratch buffer reused across layers;
   if quantize kernel has a partial-write bug at certain N values,
   the GEMM reads stale data.

## Most likely candidates (ranked by confidence)

1. **(highest) Sign extension in nibble unpack.** dp4a treats bytes as
   `int8`. My unpack stores nibbles 0..15 in low-byte positions, leaving
   bits 4..7 and bytes 1..3 zero. So byte values are 0..15 which is
   positive int8. **But:** if the compiler optimizes the unpack and
   emits a sign-extending instruction, values could become negative. To
   verify: dump emitted ISA for `load_hfq4_tile_dp4a` and confirm bytes
   are zero-extended.
2. **Per-element scale/zp formula off by a factor.** llama.cpp's Q4_0
   path uses `(8*vdr/QI4_0)` divisor on the bias term. Mine uses no
   divisor. If `QI8_1=8` and `vdr=8`, the divisor is 1 — but if I
   miscounted, the constant could be wrong.
3. **Y_STRIDE indexing.** Re-derive `tile_y[j*Y_STRIDE + 4 + ...]`
   matches what `load_q8_1_tile` actually wrote at runtime.

## Reproduction

```bash
# Coherent output (baseline):
HIPFIRE_KV_MODE=asym3 /tmp/coh_test.sh

# Gibberish (MMQ on):
HIPFIRE_KV_MODE=asym3 HIPFIRE_MMQ=1 HIPFIRE_MMQ_SCREEN=0 /tmp/coh_test.sh

# Coherent (MMQ on, but kernel skipped):
HIPFIRE_KV_MODE=asym3 HIPFIRE_MMQ=1 HIPFIRE_MMQ_SCREEN=0 \
  HIPFIRE_MMQ_DIAG_PASSTHROUGH=1 /tmp/coh_test.sh

# Standalone correctness (currently passes — does NOT reproduce the bug):
./target/release/examples/test_gfx906_mmq_correctness 4096 12288 32
```

Where `/tmp/coh_test.sh` is a one-shot daemon test for the 9B reason
prompt.

## Suggested next steps

1. **ISA dump of `load_hfq4_tile_dp4a`** — verify nibble unpack emits
   zero-extending shifts, not sign-extension.
2. **Real-weight correctness test** — extract a few real Qwen 9B layer.wo
   weight blocks from the model file, run the test against those instead
   of synthetic. If the test fails with real weights, the bug is
   weight-distribution-dependent.
3. **Per-output diff dump** — modify `mmq_screen_weight` to use my
   gfx906 MMQ kernel as the "MMQ side" and the FP16 wave64 as the
   reference. Run on real model weights. Look for which rows have
   max abs error >> 5% (catastrophic per-row failures vs. uniform 0.1%
   noise).
4. **Bisect by layer.** Add a layer-id filter (`HIPFIRE_MMQ_LAYER_FILTER=N`)
   that runs MMQ only for layer N, FP16 for all others. Find the first
   layer where the model breaks — that's the layer with the offending
   weights.

## Perf observation (secondary, not the main blocker)

With MMQ on (no screening, no K filter), prefill on Qwen 3.5 9B drops
from 140 tk/s baseline to 103 tk/s — a 26% **regression**. Profile
shows `gemm_hfq4g256_residual_mmq_gfx906` at 9.5 ms/call vs FP16 wave64's
4.4 ms/call (2.16× slower).

This is not surprising for a first-pass kernel without prefetch or vectorized
loads. Optimization tasks on the followup commit list:
- vectorize HFQ4 loads with int4 (16-byte) reads
- add L2 prefetch (plan §3.7)
- tune per-thread acc count (currently 64 floats = lots of VGPR pressure)

But none of these matter until the correctness bug is fixed.
