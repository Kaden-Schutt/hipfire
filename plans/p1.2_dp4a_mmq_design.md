# P1.2 — gfx906 dp4a MMQ residual kernel design

This document specifies the kernel for review *before* writing it. Once
this is signed off, P1.2 produces:

1. `kernels/src/gemm_hfq4g256_residual_mmq.gfx906.hip` — the dp4a kernel
2. A Rust dispatch route for it (deferred to P1.4)
3. A scratch buffer for Q8_1 activations (already exists per
   `dispatch.rs:5900: ensure_q8_1_mmq_x`)

**Weight format choice (decided 2026-05-03):** unpack HFQ4 nibbles to one
nibble per byte (int8) at LDS load time. This gives a sequential K-element
layout that pairs cleanly with our existing flat Q8_1 quantize output.
llama.cpp's alternative — keep nibbles packed in LDS, unpack on the fly
during dp4a — saves ~16 KB of LDS but requires changing the Q8_1
quantize kernel to produce an interleaved layout (low-nibble K-elements
together, high-nibble K-elements together). That's a P2 optimization;
the unpacked-at-load path here is simpler and the LDS budget still fits.

This **first commit excludes L2 prefetch.** Prefetch is a separate
follow-up so its impact can be measured cleanly. The first commit's goal
is correctness + a baseline dp4a measurement to compare prefetch against.

---

## 1. Inputs and outputs

The kernel signature matches the existing RDNA3 MMQ residual kernel so
dispatch routing can flip arch-conditionally without changing call sites.

```cpp
extern "C" __global__ void gemm_hfq4g256_residual_mmq(
    const char* __restrict__ A,         // [M × K/256] HFQ4 groups, 136 B each
    const block_q8_1_mmq* __restrict__ Xq, // [K/128 × N] Q8_1 blocks (144 B each)
    float* __restrict__ Y,              // [N × M] output (residual: Y += AX)
    int M, int K, int N, int add        // add=1 means accumulate, 0 means overwrite
);
```

Group layout (from existing FP16 wave64 kernel, confirmed):

```
HFQ4 group (136 B):
  [0..3]    float scale
  [4..7]    float zero_point
  [8..135]  128 bytes = 256 nibbles (one per K element in this group)
```

`block_q8_1_mmq` (144 B, defined in this repo):
```
  ds4[4]    half2[4] = 4 × (d, sum) for the 4 sub-blocks of 32 K-elements each
  qs[128]   int8[4 × 32] = 128 quantized activations (one Q8_1 K-block)
```

So one Q8_1 block covers 128 K-elements; one HFQ4 group covers 256
K-elements (= 2 Q8_1 blocks). This 2:1 ratio matters for the loop
structure.

## 2. Topology — wave-native (64, 2, 1)

Per Phase 0 §6 (llama.cpp-gfx906 reference):

| | Value | Why |
|---|---|---|
| Block dim | `(64, 2, 1)` | wave-native: each `threadIdx.y` = one wave64 |
| Threads/WG | 128 | = 2 × wave64 |
| `nwarps` | 2 | matches `GFX906_MMQ_NWARPS` in llama.cpp config |
| `WARP_SIZE` | 64 | physical wave size |
| Tile (M × N) | 128 × 128 | maximize arithmetic intensity (plan §3.2) |
| `MMQ_TILE_NE_K` | 32 | one K-block of int8 quants in the staged tile |

Grid:
```
grid = (ceil(M / 128), ceil(N / 128), 1)
```

Each block computes one `128 × 128` output tile.

## 3. LDS layout — `+1 int` padding (dp4a-specific), Y reloaded mid-kb

Per Phase 0 §6.5 reread of llama.cpp `mmq.cuh:170-185`:

> "K % 2 == 1 for dp4a or K % 8 == 4 for mma."

For dp4a the per-row stride is `2*MMQ_TILE_NE_K + 1 = 65` int32s. The
`+4` padding from the original plan §3.3 is for the MMA path, **not
dp4a**. Plan correction: dp4a uses `+1`.

**Definitive tile shape per llama.cpp-gfx906 (`mmq.cuh:117-166`):**

| Param | Value | Source |
|---|---|---|
| `mmq_y` | 128 | `get_mmq_y_device()` returns 128 for HIP non-RDNA1 |
| `mmq_x` | **64** | `get_mmq_x_max_device()` returns 64 for HIP w/o WMMA/MFMA |
| `MMQ_TILE_NE_K` | 32 | int-storage granularity within tile |
| `MMQ_TILE_Y_K` | 36 (= 32 + 32/QI8_1 = 32 + 4) | per-col Y stride incl. inlined ds |

**Critical structural pattern from llama.cpp `mul_mat_q_process_tile`
(`mmq.cuh:3429-3462`):** per outer kb0 iter, load **X once for the full
256-K-element span** but **load Y twice** — first half k01=[0,32), compute,
sync, then second half k01=[32,64), compute, sync. This halves Y's LDS
footprint vs staging the full 256-K Y tile.

For HFQ4 weights this is a clean fit: `2*MMQ_TILE_NE_K = 64` ints per row
in X = 64 × 4 = 256 nibbles = exactly **one HFQ4 group**. Each kb0 outer
iter advances by one HFQ4 group. The two inner Y reloads correspond to
the 2 Q8_1 blocks within that HFQ4 group (each Q8_1 block = 128 K-elements
= 32 ints/col after packing).

**X tile (weights, HFQ4 → int8 in LDS):**
```
x_qs:  128 rows × (2 * MMQ_TILE_NE_K + 1) ints = 128 × 65 = 8,320 ints = 33,280 B
       (one full HFQ4 group's nibbles per row, unpacked to one nibble per
       byte. 64 ints/row stored data + 1 int padding for bank conflict.)

x_dm:  128 half2 (one (scale, zp) per row, broadcast across all K in the group)
       = 128 × 4 = 512 B
```

**Y tile (activations, Q8_1) — only 32-K worth at a time:**
```
y[mmq_x × MMQ_TILE_Y_K] = 64 × 36 ints = 2,304 ints = 9,216 B
       (4 ints of inlined ds + 32 ints of qs per column slot.
        Refilled mid-kb0 to cover both halves of the 256-K span.)
```

**LDS budget for (mmq_y=128, mmq_x=64):**
```
x_qs:  33,280 B
x_dm:     512 B
y:      9,216 B
TOTAL: 43,008 B  (42.0 KiB / 64 KiB cap)
```

**Comfortable fit at occupancy=1, headroom for occupancy=2** (would need
86 KiB at occ=2 — doesn't fit). Production llama.cpp targets occ=1 for
this kernel on gfx906 via `__launch_bounds__(warp_size*nwarps, 2)` =
`__launch_bounds__(128, 2)` (line 3477) — they request occ=2 but the LDS
limits to 1. The compiler picks the tighter constraint.

## 4. Compute pattern — load X once, Y twice per kb0 iter

Following llama.cpp `mul_mat_q_process_tile` (`mmq.cuh:3429-3462`)
adapted for HFQ4×Q8_1:

```cpp
constexpr int mmq_y         = 128;
constexpr int mmq_x         = 64;
constexpr int nwarps        = 2;
constexpr int warp_size     = 64;
constexpr int vdr           = 8;        // dp4a calls per (i, j, k01) — 32 K-elements
constexpr int X_STRIDE      = 2*MMQ_TILE_NE_K + 1;   // 65 ints/row in x_qs
constexpr int Y_STRIDE      = MMQ_TILE_NE_K + MMQ_TILE_NE_K/QI8_1;  // 36 ints/col incl. ds

// Per-thread accumulators: float per (i, j) pair owned.
//   i sweep: i0 = 0..mmq_y step warp_size → 2 i-blocks
//   j sweep: j0 = 0..mmq_x step nwarps    → 32 j-blocks
// Each thread holds 2 × 32 = 64 floats.
float sum[(mmq_y/warp_size) * (mmq_x/nwarps)] = {0.0f};

const int groups_per_row = K / 256;
for (int kg = 0; kg < groups_per_row; ++kg) {
    // ── Load X once: full HFQ4 group → 256-K-element span in LDS ──
    load_hfq4_tile_dp4a(A, x_qs, x_dm, row0, kg, M, groups_per_row);

    // ── First half of the K span: Q8_1 K-block at kb = 2*kg ──
    load_q8_1_tile(Xq, tile_y, col0, /*kb=*/2*kg, N);
    __syncthreads();
    vec_dot_dp4a(x_qs, x_dm, tile_y, sum, /*k_offset=*/0);
    __syncthreads();

    // ── Second half: Q8_1 K-block at kb = 2*kg + 1 ──
    load_q8_1_tile(Xq, tile_y, col0, /*kb=*/2*kg + 1, N);
    __syncthreads();
    vec_dot_dp4a(x_qs, x_dm, tile_y, sum, /*k_offset=*/MMQ_TILE_NE_K);
    __syncthreads();
}

// Write back tile to Y. Residual variant: Y += AX (add=1) or Y = AX (add=0).
write_back_residual(Y, sum, row0, col0, M, N, add);
```

The compute body `vec_dot_dp4a` matches llama.cpp's pattern verbatim:

```cpp
static __device__ __forceinline__ void vec_dot_dp4a(
    const int* __restrict__ x_qs, const half2* __restrict__ x_dm,
    const int* __restrict__ tile_y, float* __restrict__ sum,
    int k_offset
) {
    // Y is staged with 4 ds half2s (= 4 ints) at the front of each col slot,
    // then 32 ints of qs. y_qs starts after the 4 ds ints.
    const int* y_qs = tile_y + 4;
    const half2* y_ds = (const half2*)tile_y;

    for (int k01 = 0; k01 < MMQ_TILE_NE_K; k01 += vdr) {  // 4 iters when vdr=8
        for (int j0 = 0; j0 < mmq_x; j0 += nwarps) {       // 32 iters when mmq_x=64
            const int j = j0 + threadIdx.y;
            const half2 ds_j = y_ds[j * Y_STRIDE/2 + (k01 + k_offset) / QI8_1];
            // Note: y_ds is half2*, so stride is Y_STRIDE/2 = 18 half2s per col.
            // For the residual MMQ path Q8_1 has 1 (d, sum) per QI8_1=8 K-elems,
            // so per col we have MMQ_TILE_NE_K/QI8_1 = 4 ds entries.

            for (int i0 = 0; i0 < mmq_y; i0 += warp_size) {  // 2 iters when mmq_y=128
                const int i = i0 + threadIdx.x;

                int sumi = 0;
                #pragma unroll
                for (int v = 0; v < vdr; ++v) {
                    const int x_int = x_qs[i * X_STRIDE + k01 + k_offset + v];
                    const int y_int = y_qs[j * Y_STRIDE + k01 + v];
                    sumi = __builtin_amdgcn_sdot4(x_int, y_int, sumi, false);
                }

                // Scale/zp correction. HFQ4 affine × Q8_1 symmetric → 2 terms.
                const half2 dm_i = x_dm[i];
                float2 dmf = __half22float2(dm_i);
                float2 dsf = __half22float2(ds_j);
                float scale_w = dmf.x, zp_w = dmf.y;
                float d_x     = dsf.x, sum_x = dsf.y;

                int idx = (j0 / nwarps) * (mmq_y / warp_size) + (i0 / warp_size);
                sum[idx] += scale_w * d_x * (float)sumi    // signed dot product
                          + zp_w    * sum_x;               // bias correction (vdr=QI8_1, divisor=1)
            }
        }
    }
}
```

### 4.1 Notes on the compute structure

- **Per-element correction.** llama.cpp's `vec_dot_q8_1_q8_1_impl` divides
  the bias term by `(QI8_1 / vdr)`. With vdr=8 and QI8_1=8, the divisor
  is 1 — no division needed. Verify this when implementing; if vdr ≠ 8 the
  divisor must be applied.
- **No tile<> abstraction.** Direct LDS reads. Per Phase 0, the tile<>
  abstraction in the current MMQ kernel is RDNA3-shaped and produces
  out-of-bounds indices on wave64 if reused naively.
- **Per-thread acc count:** 64 floats × 4 B = 256 B = 64 VGPRs. Plus 8
  i32 dp4a temps (8 VGPRs) + scale/zp temps + indices ≈ **80–100 VGPRs**.
  Per Phase 0 §3, target ≤84 for occupancy=3, ≤128 for occupancy=2.
  We'll likely land at occupancy=2. Confirm empirically with rocprof.

## 5. Tile loaders

### 5.1 `load_hfq4_tile_dp4a` — HFQ4 weights → int8 in LDS

Each Q8_1 K-block covers 128 K-elements. One HFQ4 group covers 256
K-elements. So:
- Even kb (kb % 2 == 0): load the **first half** of an HFQ4 group
- Odd kb (kb % 2 == 1): load the **second half** of the same HFQ4 group

The HFQ4 group index is `kb / 2`. The byte offset within the group's
quant payload is `(kb % 2) * 64` (each half = 64 bytes = 128 nibbles).

```cpp
static __device__ __forceinline__ void load_hfq4_tile_dp4a(
    const char* __restrict__ A,
    int* __restrict__ x_qs,        // 128 × 65 ints
    half2* __restrict__ x_dm,      // 128 half2
    int row0, int kb, int M, int K
) {
    const int groups_per_row = K / 256;
    const int kg = kb / 2;            // HFQ4 group index
    const int half_offset = (kb & 1) * 64;  // byte offset within the group's quant payload

    // 128 rows × 16 ints/row to load = 2048 ints per kb iteration.
    // 128 threads → 16 ints/thread. Each thread loads 16 contiguous ints
    // for one row, but we'd rather distribute by row to maximize coalesced
    // reads from HBM. So: 128 threads × 16 ints = 1 thread per (row, int_in_row).
    //
    // Actually, more aligned with llama.cpp's pattern: each thread handles
    // a few rows, each row has all its ints loaded by one thread.
    //
    // Simpler: tid (0..127) → row = tid, then this thread loads all 16 of its row's ints.
    // 128 threads × 16 b32 reads each = sequential per-row HBM reads.

    const int tid = threadIdx.y * blockDim.x + threadIdx.x;  // 0..127
    const int i = tid;                                        // row index in tile
    const int row = (row0 + i < M) ? (row0 + i) : (M - 1);    // boundary clamp
    const char* gp = A + ((long long)row * groups_per_row + kg) * 136;

    // Scale & zp (only relevant on kb iterations that hit this group; load
    // both halves' scale/zp into x_dm — same value because it's per-group)
    if (i < 128) {
        const float sc = __builtin_bit_cast(float, *(const unsigned int*)gp);
        const float zp = __builtin_bit_cast(float, *(const unsigned int*)(gp + 4));
        x_dm[i] = make_half2((_Float16)sc, (_Float16)zp);
    }

    // Load 64 bytes of nibbles for this Q8_1 block (128 nibbles → 32 ints
    // staged as low-nibble in each byte → 64 ints? Need to recheck packing.)
    //
    // Wait: 128 K-elements = 128 nibbles = 64 bytes raw. The MMQ tile stores
    // them as int8 (one nibble per byte, low 4 bits) so the dp4a sees them
    // as int8s. That's 128 int8s = 32 ints in the tile per row per kb.
    //
    // But our row stride in LDS is 65 ints (per §3). Where does the K dim go?
    //   x_qs[i * 65 + k01 + v]  → k01 ∈ [0, 32) step 8, v ∈ [0, 8). So the
    //   per-row int span is exactly 32 ints: indices [0..31] of the row.
    //
    // 32 ints per row per Q8_1 block × 128 rows = 4096 ints loaded per kb.
    // 128 threads → 32 ints/thread. Loop unroll factor 32 inside the loader.
    //
    // Each load: read 4 contiguous nibbles from the HFQ4 payload, expand
    // each nibble to one byte (low 4 bits, zero-extended), pack into int.

    #pragma unroll
    for (int u = 0; u < 32; ++u) {
        // Each unroll loads 4 nibbles (= 1 byte from HFQ4 payload) and
        // produces 1 int with 4 int8s of value 0..15.
        // tid==i==row; u==int-in-row; byte offset within payload = half_offset + u*4
        // Wait: we have 32 ints per Q8_1 block per row, each int = 4 nibbles
        // = 4 K-elements. So 32 × 4 = 128 K-elements per Q8_1 block. Correct.
        // Bytes: 32 × 2 nibbles/byte = wait no. 32 ints × 4 nibbles = 128
        // nibbles = 64 bytes. So byte offset = half_offset + u*2 (each int reads
        // 2 bytes = 4 nibbles).

        const unsigned int qs0 = *(const unsigned int*)(gp + 8 + half_offset + u * 2);
        // qs0 has 8 nibbles; we need 4 of them as low bytes in our output int.
        // Standard trick: even u takes low 4 nibbles, odd u takes high 4 nibbles.
        // But since u steps in 4-nibble chunks, this is wrong. Need to think...
        //
        // Actually: 32 ints per row per Q8_1 block. Each int is 4 nibbles.
        // 32 × 4 = 128 nibbles. We have 128 nibbles in the half. So u runs
        // 0..31 and reads 4 contiguous nibbles each. Each `u` covers exactly
        // 4 nibbles = 2 bytes. So byte offset = half_offset + u * 2.
        //
        // Read 2 bytes (= 16 bits = 4 nibbles), unpack to one int:

        // ... details to finalize during implementation. Confirm against
        // existing load_hfq4_tile() at line 232-263.
        x_qs[i * 65 + u] = ...;  // pseudocode
    }
}
```

**Open question for implementation**: the existing `load_hfq4_tile` at
line 232–263 reads 4 bytes via `qs0 = *(uint*)(gp + 8 + txi*4)` and packs
8 nibbles into 2 ints. That's because RDNA3 staged 76 ints/row =
2*MMQ_TILE_NE_K + 12 padding. For dp4a with 65 ints/row (32 ints per
Q8_1 block × 2 blocks fit per HFQ4 group, so per Q8_1 block we use 32
ints per row, with kb-toggling), the indexing is different.

**This needs careful implementation work.** Will revisit during coding.

### 5.2 `load_q8_1_tile` — Q8_1 activations from `Xq`

Q8_1 blocks come pre-quantized in `Xq` (already `block_q8_1_mmq` format).
Each block is 144 bytes for one (k-block, token) pair. Layout per block:
- 8 bytes: 4 × half2 (d, sum) — one per 32-K-element sub-block
- 128 bytes: 128 int8s

For tile load: each block → 32 ints in y_qs and 4 half2s in y_ds.

## 6. Write-back

Each thread holds `sum[idx]` for its `(j0/nwarps × mmq_y/warp_size) +
(i0/warp_size)` outputs = 2 × 32 = 64 floats.

For each (i, j) the thread is responsible for, write to `Y[(col0+j) × M + (row0+i)]`:
- if `add == 0`: `Y[...] = sum[idx]`
- if `add == 1`: `Y[...] += sum[idx]`

Boundary check: don't write if `row0+i >= M` or `col0+j >= N`.

This matches the existing kernel's write-back; copy-adapt.

## 7. Sign-extension correctness (verifies plan §4)

HFQ4 nibbles are unsigned 0..15. After unpack into int8 lanes (one nibble
per byte, zero-extended), values are 0..15 = within int8 positive range.
**`__builtin_amdgcn_sdot4` interprets each byte as signed int8 — values
0..15 are safe (no MSB set).** No biasing needed.

Q8_1 activations are already int8 with magnitude up to 127 (symmetric, no
zp). `sdot4` on (HFQ4_unpacked, Q8_1) is correct.

## 8. What's deferred to follow-up commits

- **L2 prefetch.** Inline asm `global_load_dword` issued by spare lanes
  during compute to warm L2 for the next kb iteration. ~50 LOC. Will be a
  separate commit so its impact is measurable.
- **Tile size sweep.** P2 tuning — try (64×128), (64×64), (128×64).
- **`gemm_hfq4g256_residual_mmq_full_add` and `_full_set` variants.** The
  RDNA3 path has these (no boundary checks when M and N are divisible by
  128). Add for symmetry once base kernel is correct.
- **Multiple precompiled `mmq_x` shapes.** llama.cpp dispatches to
  pre-compiled instances of the kernel by batch size; we'll add this in P2.

## 9. Risks and mitigations

| Risk | Probability | Mitigation |
|---|---|---|
| LDS bank conflicts on dp4a tile | Medium | rocprof `LDSBankConflict` after first compile; if >5%, try +0 / +2 / +4 padding |
| VGPR spills (>128 VGPRs) | Medium | rocprof `arch_vgpr` after first compile; if spill, reduce mmq_x to 32 or break into more accumulator chunks |
| Wrong scale/zp formula on HFQ4×Q8_1 | High | small-input correctness test against FP16 wave64 reference; max abs error < 5% per output |
| Q8_1 tile load races on wave64 | Low | each thread writes unique LDS index; `__syncthreads` between load and compute |
| Q8_1 quantize already broken | Low | already compiles; standalone test in P1.5 |
| Off-by-one on HFQ4 sub-half (kb even/odd) | High | unit test that small inputs match FP16 wave64 reference exactly within quantization noise |
