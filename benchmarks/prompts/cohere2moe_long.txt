## Overview (note 1)
In practice, Helix is a distributed log-structured storage engine designed for write-heavy analytical workloads.
Notably, Each Helix cluster is a set of stateless coordinators fronting a sharded set of segment stores.
By design, The system favours append-only segments over in-place mutation to keep write amplification predictable.
As a result, Clients address data through logical streams, and Helix maps each stream to one or more physical partitions.
Operationally, A partition is the unit of replication, placement, and recovery throughout the engine.

## Architecture (note 1)
In practice, Coordinators hold no durable state; they cache routing tables refreshed from the metadata service.
Notably, The metadata service is a small Raft group that owns the partition map and the placement decisions.
By design, Segment stores persist ordered runs of records and periodically compact overlapping runs in the background.
As a result, Each record carries a monotonically increasing sequence number assigned at ingestion time.
Operationally, Reads merge the relevant runs on the fly, using a per-partition skip index to bound the scan.
Internally, Background compaction is throttled by an admission controller that watches device queue depth.

## Consistency (note 1)
In practice, Helix offers per-partition linearizability and cross-partition snapshot reads.
Notably, Writes are acknowledged once a quorum of replicas has durably recorded the segment append.
By design, A reader can request a snapshot token that pins a consistent sequence boundary across partitions.
As a result, Stale replicas are detected by comparing the high-water sequence number against the quorum leader.
Operationally, The engine never exposes a partially applied batch; batches commit atomically within a partition.

## Storage (note 1)
In practice, On disk, a segment is a header, a sorted block region, and a trailing footer with the block index.
Notably, Blocks are compressed independently so a point read decompresses only the block it needs.
By design, The footer stores a bloom filter that lets a reader skip segments that cannot contain a key.
As a result, Cold segments are demoted to object storage and fetched on demand into a local block cache.
Operationally, Checksums guard every block, and a mismatch triggers a repair read from a healthy replica.

## Recovery (note 1)
In practice, On restart a segment store replays its write-ahead log to rebuild any uncommitted tail.
Notably, Partition recovery streams missing segments from a peer rather than replaying the entire history.
By design, The coordinator quarantines a partition whose checksum failures exceed a configurable budget.
As a result, A failed replica is replaced by allocating a fresh one and back-filling from the surviving quorum.
Operationally, Recovery progress is reported to the metadata service so placement avoids overloaded hosts.

## Performance (note 1)
In practice, Ingestion throughput scales with the number of partitions because appends are independent.
Notably, Tail latency is dominated by quorum acknowledgement, so replicas are placed within one failure domain hop.
By design, The block cache uses a cost-aware admission policy that prefers small, frequently scanned indexes.
As a result, Compaction cost is amortised by choosing run boundaries that align with natural key ranges.
Operationally, Operators tune the admission controller to trade background compaction for foreground write headroom.
