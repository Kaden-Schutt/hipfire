# PR notes — loop-guard default off + medium think-cap default + spec-decode honors the cap

Branch: `feat/mtp-config-default` (base `4ba5aeed`). Draft notes for the PR; file
later tonight.

## Problem

Serving qwen3.6 (27B dense, a3b MoE) at the model's registry-default sampling
(`temp=1.0`, added `e9ad7b8a`, 2026-06-28) produced **empty / non-committal
output**: the model reasons in `<think>` but never emits a final answer.
Two distinct, independent causes were isolated:

1. **Loop-guard false-positive (lobotomy).** The runtime n-gram loop guard
   (`crates/hipfire-runtime/src/loop_guard.rs`, added #125 `ec11b76a`
   2026-05-03) fires when *any 4-gram repeats ≥8× in the trailing 256 tokens*
   (`HIPFIRE_NGRAM_LOOP_THRESHOLD` default **8**). On enumeration-heavy
   reasoning at temp=1.0 the markdown bullet scaffold (`\n - **`) repeats ≥8×
   **inside `<think>`**, the guard force-EOSes mid-think, and the truncated
   output is all reasoning → **empty content channel**. It was dormant at the
   prior arch-default `temp=0.3` and only surfaced once the temp=1.0 registry
   default landed (~1 day before this work). Proof: `HIPFIRE_NGRAM_LOOP_THRESHOLD`
   8↔0 deterministically flips 27B from 4-empty↔8/8-clean, same binary, same
   prompt (generation is deterministic — guard-off is byte-identical across two
   binaries). The guard's firing message goes to the daemon→CLI stdout pipe (not
   `serve.log`), which is why it stayed invisible.

2. **Uncapped runaway thinking.** Independently of the guard, at temp=1.0 with
   thinking on + no think budget, the model sometimes reasons straight to the
   `max_tokens` wall without ever closing `</think>` → no answer. Confirmed on
   **AR, DFlash, and MTP** (the same turn — a code-generation prompt — degenerates
   identically across all three). The medium think cap (2048) fixes it: it
   force-closes `</think>` (`generate`/`generate_multi` splice the continuation
   through KV and keep generating) → the model commits an answer. The capped
   fleet battery is 8/8 clean where the uncapped one was not. The cap closes
   gracefully and does NOT "flip the model out" the way the guard's hard EOS did.

   BUT: a think cap currently routes thinking-on requests to AR and **disables
   DFlash/MTP** (`daemon.rs:6955` `budgeted_thinking_needs_ar = max_think_tokens > 0
   && !ClosedThink`), because DFlash's force-close did not continue into the
   answer. So "default the cap" naively = "spec-decode off by default" — a
   regression against the whole spec-decode effort.

## Fix (3 parts, in order)

1. **Disable the loop guard by default** — `ngram_loop_threshold` default 8 → 0
   (`config.rs`). Removes the FP-lobotomy on 27B. The guard's only legitimate
   role (answer-phase repetition) is marginal + small-model-only and net-negative
   at temp=1.0; the DFlash coherence gate uses its OWN inline detector, not the
   daemon guard, so gates are unaffected. Opt back in with
   `HIPFIRE_NGRAM_LOOP_THRESHOLD=N`.

2. **Default the medium think cap** — make `thinking_budget="med"` (2048) actually
   enforce (today it resolves to "non-explicit" → uncapped, `cli/index.ts`).
   Fixes runaway thinking → the model commits an answer.

3. **Make spec-decode honor the cap (parity with AR, like sampling)** — drop the
   `budgeted_thinking_needs_ar` AR-routing and wire the DFlash + MTP force-close
   to continue into the visible answer after the forced `</think>`, exactly as
   AR's `generate`/`generate_multi` already do. So a budgeted-thinking request
   keeps DFlash/MTP engaged AND commits an answer.

   **Design decision: TRUE spec-decode continuation, not AR fall-back.** The
   answer after the forced `</think>` is generated by the SAME spec-decode path
   (DFlash drafter+verify / MTP head), not by silently dropping to AR. Falling
   back to AR for the answer would mean a user who selected DFlash/MTP sees an
   AR-generated answer — misrepresenting spec-decode throughput. Both halves of
   the turn (the capped think span AND the answer) run on the selected
   spec-decode path; the verify step keeps it lossless == AR-at-(sampling), so
   coherence is preserved.

   - **DFlash** (`spec_emit.rs`): the think-budget force-close now INJECTS the
     `</think>\n\n` continuation token IDs into the emitter's `forced` queue
     (`take_forced`) instead of streaming a display string + `ThinkCap`. The
     daemon's existing `forced_after` loop (built for cohere2moe's guards)
     advances the target over them, re-feeds them through `observe`, and
     continues — no daemon-loop change needed. A one-shot `think_force_closed`
     latch hard-stops a pathological `<think>` re-open (mirrors the AR guard).
   - **MTP** (`generate_qwen35_mtp`): at the block boundary (not mid-block, so
     the emitted stream stays consistent with the trunk KV `spec_step` already
     advanced), splice `[last_committed] ++ </think>\n\n[..n-1]` through
     `prefill_trunk_and_mtp_cache` (advances trunk KV/DN + MTP head cache +
     refreshes `prev_hidden`), emit the continuation, and CONTINUE the spec
     loop with the final close token deferred as `last_committed` — exactly
     mirroring the prefill→spec-loop handoff invariant.

   uncapped `122.2` tok/s — the force-close path costs nothing (it runs once per

   MTP-off `143.7` vs MTP-on `119.8` — the a3b MTP-on<off gap is **pre-existing

   *better* on-number + fixes the fails).
3. **fewer empty/overrun fails**: on the 3-turn coding battery, my change took
   MTP-on from `1 empty/overrun` → `0`. Behavior-correct.

## Multiturn spec-decode measurements (k9lin gfx1100, 8-turn coding session, sampled temp=1.0)

These are **separate, pre-existing findings (NOT introduced by this PR)** — the cap
change is perf-neutral on all of them — but they bound where spec-decode is worth
defaulting. All numbers are daemon `decode_tok_s` (decode-only), same-file
`mtp_mode` toggle (AR = the same `*-mtp` bundle with the head ignored), MTP
`p_min=0.4` default unless noted.

**MTP @ fwht3 KV (the durable mode):**

| arch / model | AR | MTP | Δ | per-turn trend |
|---|---|---|---|---|
| **27b dense** (`qwen3.6-27b.mq4-mtp`) | 42.9 | **52.9** | **+23%** | DURABLE — +13→+35% turns 1-8, 0 fails, recall 3/3 |
| a3b MoE mq4p (`…a3b.mq4p-cvs-mtp`) | 114.2 | 106.3 | **−6%** | net-neg (dilution); 0 fails |
| a3b MoE mq4r (`…a3b.mq4r-cvs-mtp`) | 146.8 | 126.4 | **−14%** | net-neg (dilution) |

**MTP @ q8 KV (shows the erosion fwht3 fixes — DENSE only):**

| arch | AR | MTP avg | per-turn margin vs AR |
|---|---|---|---|
| **27b dense** | 41.9 | 48.3 (+15%) | **ERODES**: +29% (turn2/ctx2k) → **−2%** (turn8/ctx9k) |
| a3b MoE mq4r | 139.2 | 122.6 (−12%) | net-neg throughout |

→ **fwht3 is the lever for dense multiturn durability**: at ctx<4.5k q8≈fwht3, but
above ~6k q8 erodes (verify becomes K-read-bound, q8's K-read grows with ctx) while
fwht3 (cuts K-read 2.7×) holds. Confirms memory's +19.8% @ctx9.8k empirically.

**Single-turn (one request, code prompt):** a3b MTP **+1.6% sampled / +14.8% greedy**
— the single-prompt win that the documented ctx-erosion eats on multiturn.

**`p_min` (confidence-truncation) sweep on a3b mq4p @ fwht3:** AR 114.2;
p_min 0.0→104.2, 0.4→107(default), 0.6→**107.4**, 0.8→106.9. Confidence-truncation
is a real but small lever (**+3%**, τ drops as chains shorten) — it does NOT flip
a3b above AR. (This is DSpark's lever, #484, in miniature.)

### Why a3b MoE is multiturn-weak — and why flash attention / prefix caching / DSpark don't fix it

The mechanism is **dilution**: MTP's win is amortizing weight-loads across K
verified tokens; as ctx grows, the per-token **KV-read** of the verify grows O(N)
and dominates, shrinking MTP's fixed weight-save fraction until it goes underwater.
On dense the weight-save margin is large enough to survive the O(N) read (esp. with
fwht3 trimming the slope) → durable. On a3b MoE (~3B active) the margin is tiny → it
dilutes.

Three things that look like fixes but aren't, with the reason:

- **Flash attention** — already in use (`attention_flash_q8_0_tile.hip` etc.). It
  makes the KV-read **bandwidth-optimal** (online softmax, no O(N²) matrix) but does
  **not reduce the O(N) read *volume*** — decode must still read all N keys/values.
  It's the optimal *execution* of an O(N) op, not a sublinear one. Dilution is the
  O(N) *growth*, which no attention kernel removes.
- **Prefix caching** — `decode_tok_s` is decode-only (`t_end − t_prefill`), so it is
  **prefill-independent**: caching is a prefill/TTFT optimization and cannot move the
  decode deficit. (Aside: MTP currently reports `cached_tokens:0` and re-prefills the
  whole conversation each turn while AR has the LCP cache — so end-to-end MTP
  multiturn is *worse* than the decode-only −6%; adding MTP prefix caching closes
  that gap but not the dilution.)
- **DSpark (#484)** / confidence-truncation — raises the curve (+3% via p_min proxy,
  maybe +6-11% with a trained head on code) but does **not flatten the erosion
  slope** → shifts the crossover later, doesn't make a3b durable multiturn.

The only thing that flattens the slope is **sublinear KV access**: sliding-window
(O(N)→O(W); the flash kernel *has* a `window` param) or linear attention (DeltaNet,
O(1) state). a3b can't use windowing because its DeltaNet recurrent-state ratio
**R̄≈0.39** is too low — dropping old KV loses unrecoverable context → confident-wrong
(`feedback_a3b_r_not_acceptable`; eviction is already force-gated off under
spec-decode and excluded for a3b in `cli/index.ts`). So a3b-MoE multiturn spec-decode
is blocked on the **attention mechanism / R̄**, not on MTP/DSpark/flash/cache tuning.

**Strategic conclusion:** ship spec-decode where it durably wins — **dense @ fwht3
(+23%)** — and default a3b to AR-multiturn / spec-single-turn. Raising a3b's R̄ (so
windowing becomes safe) is the real unlock; tracked separately from this PR.
